== Abstract

https://ogcapi.ogc.org/#standards[OGC API Standards] define modular API building blocks to spatially enable Web APIs in a consistent way.
The https://www.openapis.org[OpenAPI] specification is used to define the API building blocks.

This Standard ("Part 3 - Publish/Subscribe") defines how publish/subscribe protocols are used to asynchronously exchange CS API resources and their respective metadata and defined lifecycle events.
It builds on the resource model and HTTP interface defined in {ogcapi-cs-1} and on the dynamic data resource types defined in {ogcapi-cs-2}. It also extends the message and payload framework defined in OGC API - Pub/Sub by specifying the resource events, resource data messages, and protocol bindings specific to Connected Systems.

Part 3 provides a window into CS API and improves discoverability of resources as they become available for devices and systems already using popular pub/sub frameworks.
It complements the REST API defined in Parts 1 and 2 and also supports standalone Resource Event deployments without an associated HTTP service. Clients need not implement both HTTP and Pub/Sub interfaces.

Two categories of pub/sub messages are defined. *Resource events* are CloudEvents-formatted notifications that signal the creation, update, or deletion of any CS API resource; they identify the affected resource and may include optional JSON content as specified by the Resource Events requirements class. *Resource data messages* carry full resource representations using the native CS API encodings (JSON, SWE Common JSON, SWE Common Text, SWE Common Binary) and are intended for low-latency streaming of CS API resources, as well as for the registration of new resources from publishing clients.

CloudEvents provides a common, standardized notification envelope and does not require any cloud infrastructure. Resource Data Messages use native resource encodings without a CloudEvents envelope.

Protocol bindings define how these messages are exchanged over specific pub/sub transports.
The common message requirements are independent of transport. MQTT is the first planned binding in this document and a primary worked example; its binding remains under development. Additional bindings may be published separately and need not become official parts of this Standard to satisfy its applicable requirements. Implementing another binding does not require implementing MQTT.

== Security considerations

Security considerations detailed in {ogcapi-cs-1} and {ogcapi-cs-2} also apply to this Standard.
Additional security requirements specific to publish/subscribe interactions around the prevention of unauthorized publishing on server-controlled channels and the propagation of resource-level access control to event subscriptions are stated in the relevant requirements classes of this Standard.
