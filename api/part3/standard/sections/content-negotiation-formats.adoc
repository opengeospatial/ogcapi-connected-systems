Support for multiple representations of a resource-data stream is optional. Each offered stream provides at least one permitted media type under /req/resource-data-messages/representation-offering. An implementation offering several representations provides explicit selection through separate channels or, where supported, an established transport content-negotiation mechanism.

The binding defines the concrete mechanism, and the service description tells clients which representations are offered and how to select them. Supporting an encoding elsewhere in the API does not automatically offer it through Pub/Sub. Implementations may optimize when they produce representations, but preserve the advertised channel behavior and negotiated selections. Subscriber-count detection is not required.

Content-type metadata identifies a message's representation; it does not itself negotiate a representation. For example, MQTT's Content Type property describes the published payload. By contrast, SIP event subscriptions use `Accept` in `SUBSCRIBE` to specify permitted `NOTIFY` body formats (https://www.rfc-editor.org/rfc/rfc6665.html#section-3.1.3[RFC 6665, section 3.1.3]). This is a negotiation precedent, not a definition of a CS API SIP binding.

For example, a service may advertise an Observation stream as `application/json` only. A service offering both `application/json` and `application/swe+binary` may advertise separate channels for the two representations. A client selects the advertised channel for its desired representation; support for another encoding on an HTTP endpoint does not add a Pub/Sub offering.

Bindings may use the normalized format-name convention below for channel selection. Channel syntax remains a binding responsibility. Normalization discards media-type parameters and can collapse distinct types to the same name, so the service description and selection mechanism must still distinguish every offered representation unambiguously.

[NOTE]
.OM JSON and `application/json`
====
*OM JSON and Part 2 observation JSON are the same CS API encoding.* Older CS API examples label it `application/om+json` (`om-json`); the media type specified by {ogcapi-cs-2} is `application/json`, with normalized format name `json`. This Standard uses the Part 2 media type.
